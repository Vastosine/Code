# 出题流程模板（从 U721285 提炼）

> 适用：在洛谷出**自建题**（U 题库 / 团队题库）。目标是「选手投诉不了」。
> 每一步都有对应的坑，坑都是真实踩过的，写在每节末尾。

## 目录约定

```
OI/luogu/make-problem/<题号>/
├── problem.md            题面（约束必须与数据一致！）
├── std.cpp               标准程序
├── std_dinic.cpp         std 的另一种实现（对拍用）
├── brute.cpp             暴力（仅小规模，不依赖任何理论）
├── gen.cpp               数据生成器（参数显式列表化）
├── data/                 最终数据 1.in/1.out … N.in/N.out
├── data_v2/              重造数据时的对照目录（不覆盖旧数据）
└── README.md             约束、测试点意图、验证记录、复现命令
```

---

## 阶段 1：建模

把真实问题抽象成算法问题，写清**三件事**：

1. **输入是什么**（元素、数量、关系）
2. **约束是什么**（哪些是"保证"，哪些是"可能"）
3. **要输出什么**（判定 / 计数 / 方案）

**落笔前先问：这个问题等价于什么经典模型？**
（U721285 是「带容量的二分匹配 → 最大流」。）

**坑**
- 从真实场景抽象时，容易把场景里的隐含条件丢掉或加多。**写出"等价于"那一句，然后反过来验算样例。**

---

## 阶段 2：std

**先写最直白的正确实现，再优化。** 顺序反了会写出"快但错"的东西。

**坑**
- **别用固定尺寸容器装稀疏数据**。`w.assign(n, vi(m))` 在 `n=m=10⁴` 时是 400 MB；
  边数只有 5×10⁴ 时应该用邻接表。
  （U721285 原 std 就是这个，重测峰值 389 MB。）
- 多测要**彻底重置**全局数组，`assign` 比 `clear` 安全。
- 关掉 iostream 同步：`ios::sync_with_stdio(0), cin.tie(0)` —— 大输入实测 **1.5–1.7×**。
- 调试输出（`cerr << clock()`）**交题前删掉**。

---

## 阶段 3：验证链（最重要的一步）

**"我的 std 是对的"不能靠"我觉得"。必须三方对拍。**

```
① std  vs  独立实现的第二种算法
② std  vs  暴力（小规模、不依赖理论）
③ 三方全一致  →  才允许拿 std 的输出当 .out
```

**具体做法**

```powershell
# ② 小规模暴力：完全不用流/图论，直接回溯
#    随机 3000 组 tiny 数据（n,m≤4，值≤3），diff 两份输出
cmd /c "brute.exe < tiny.in > tiny.brute"
cmd /c "std.exe   < tiny.in > tiny.std"
# 期望：0 差异
```

**坑**
- **拿未验证的 std 生成 `.out`，等于把 bug 焊进数据里。**
- 比较输出时**先统一换行**（`\r\n` vs `\n`），否则会误判"全错"。
  ```powershell
  function Norm($p){ ((Get-Content $p -Raw) -replace "`r","").Trim() }
  ```
- `.out` 是 0 KB 不一定是空文件——`c` 小时的输出本来就不足 1 KB。

## 阶段 4：数据

**生成器三原则**

1. **参数显式列表化**，每个测试点一个 `Spec` 结构，注释写意图。
   （原 `dataGenerator.cpp` 把参数散在注释里，导致线上数据与生成器常量对不上，无法复现。）
2. **生成 / 判题分离**：生成器只写 `.in`，`.out` 由 std 单独跑。
3. **逐组校验**：任何数值越界就重抽该组。

```cpp
struct Spec { int id, c, n, m, maxK, sumTag, maxDem, maxSup, mode; };
static vector<Spec> specs = { /* 每个点一行，写清意图 */ };
```

**数据自检清单**

- [ ] `c`、`n`、`m`、数值上下界 **全部** 在题面范围内（逐组解析 `.in` 核对，不靠感觉）
- [ ] 每个测试点都含 `0` 和 `1` 两种答案（否则「永远输出 0/1」的假解能过）
- [ ] 边界点：`n=1`、`m=1`、需求>供给、完全无解、恰好够用
- [ ] 构造类数据（保证 YES / NO）要有兜底校验

**坑**
- **构造 YES 时不要削减已有用量**。U721285 的生成器里 `if (sup[j] > 2999) sup[j] = 2999;`
  把"刚好可行"砍成"不可行"，整组答案变成 0，而我还以为构造生效了。
- `WriteAllText("x.cpp", ...)` 用**相对路径**会写到 .NET 进程的 CWD，不是你的 shell CWD。**永远用绝对路径。**
- 别一边改生成器一边覆盖旧数据。**新数据放 `data_v2/`，验证通过再替换。**

---

## 阶段 5：题面自检

逐条对，缺一条就可能被投诉：

- [ ] **约束与数据一致**（最容易被投诉的一条）。改题面后要重新核对数据，或反过来重造数据。**核对前先确认你看的是线上最新题面，不是本地旧文档。**
- [ ] **歧义点全部显式声明**。典型：共享 vs 独立、是否允许重复、是否允许空集、能否为 0。
- [ ] **样例有解释**，尤其是答案非平凡的那个。
- [ ] **子任务**：至少 2–3 档，否则区分度极低（全对或全零）。
- [ ] **时限 / 内存**与实际数据规模匹配。

## 语言侧

| 语言 | 注意 |
|---|---|
| C++ | 关同步；大数组别放栈上；`vector` 比 `new[]` 安全 |
| Java | **别用 `Scanner`**（几十万整数会吃掉 3–4 秒）。手写 `byte[]` + 解析，或 `BufferedReader`+`StringTokenizer` |
| Java | `List<List<Integer>>` 的装箱在循环里会拖慢；用 `int[]` 边表 |
| Java | 递归深度大要 `-Xss`；本题图只有 4 层，不用 |

**U721285 的实测**：同一算法，`Scanner` → 手写快读，**12.70 s → 0.1 s**。

## 交付前三问

1. **答案可复现吗？** 换一个人按 README 能重新生成全部数据吗？
2. **约束对得上吗？** 打印出每个点的实际最大值，与题面逐项比对。
3. **假解能过吗？** 写一个「永远输出 1」和「永远输出 0」，确认它们在每个点都挂。
